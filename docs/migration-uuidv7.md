# qubar 主键迁移至 UUIDv7 规划文档

> 状态:规划已确认,待实施
> 中间件:PostgreSQL 18(原生 `uuidv7()`)
> 适用范围:全量主键 + 外键 `int64` → `UUIDv7`

---

## 0. 已确认的关键决策

| # | 决策点 | 结论 | 影响 |
|---|---|---|---|
| D1 | UUID 生成位置 | **Go 端 `BeforeCreate` 生成**,不依赖 DB 默认值 | 避免 GORM 零值覆盖;保证 Create 后 ID 立即可用(如 `CreateCircle` 后读 `circle.ID`) |
| D2 | 零值哨兵 | **NULLABLE 列 + Go 指针 `*uuid.UUID`** | `root_id / reply_to_id / parent_id / category_id` 等改可空;查询 `=0`→`IS NULL`,`>0`→`IS NOT NULL` |
| D3 | Category 表 | **一并迁移为 UUID** | 种子 SQL 必须固化具体 UUID(不可随机),`circle.category_id` 同步改 UUID |
| D4 | 数据迁移 | **无需迁移**(新服务器、无数据) | 直接按新 DDL 建表;不涉及回填、FLUSH、reindex、停机窗口 |

---

## 1. 背景与结论

当前所有表主键为 `BIGINT GENERATED BY DEFAULT AS IDENTITY`,Go 侧为 `int64`,并在 Redis 缓存键、ES 文档、MQ 消息、sa-token 会话、S3 路径中流转。

**迁移目标**:全部改为 UUIDv7。

**UUIDv7 是本项目正确选择的原因**:
1. **PG18 原生支持** — 内置 `uuidv7()`,可作列默认值,无需 sequence/触发器。
2. **时序可排序(决定性优势)** — UUIDv7 前 48 位为毫秒级 Unix 时间戳,**字典序 == 时间序**。本系统大量依赖「按 `id DESC` 取最新」(ES 排序、`search_after`、评论 keyset 游标分页),迁移后这些语义天然保留;若用 UUIDv4 会全部失效。
3. **库已就位** — `github.com/google/uuid v1.6.0`(支持 `uuid.NewV7()`)已在 `go.mod` 依赖树中(现为 indirect,需提升为 direct)。

**主要工作量在周边系统**:DB 改类型 + 默认值即可,但 ID 以 `int64` 流转于各存储/中间件,需逐层同步改造。

## 2. UUID 类型与生成方案(基础层)

### 2.1 依赖

`go.mod` 已含 `github.com/google/uuid v1.6.0`(indirect)。实施时:
```bash
go get github.com/google/uuid@v1.6.0   # 提升为 direct 依赖
```

> `google/uuid` v1.6.0 起提供 `uuid.NewV7()` / `uuid.NewV7FromReader()`。`uuid.UUID` 为 `[16]byte`,已实现 `database/sql/driver.Valuer` 与 `sql.Scanner`,GORM + postgres 驱动能正确映射到 PG `uuid` 类型,**无需自定义 Scanner/Valuer**。

### 2.2 推荐:提取公共 Base Model

所有 8 个 model 重复定义了 `ID` + `CreateTime` + `UpdateTime`,且 ID 生成逻辑需统一。建议抽取公共基类,集中生成 UUIDv7:

```go
// pkg/server/model/base.go
package model

import (
    "time"

    "github.com/google/uuid"
    "gorm.io/gorm"
)

// BaseModel 公共字段:UUIDv7 主键 + 创建/更新时间
type BaseModel struct {
    ID         uuid.UUID `json:"id" gorm:"type:uuid;primaryKey;column:id"`
    CreateTime time.Time `json:"create_time" gorm:"column:create_time;autoCreateTime"`
    UpdateTime time.Time `json:"update_time" gorm:"column:update_time;autoUpdateTime"`
}

// BeforeCreate 在插入前生成 UUIDv7(零值才生成,允许外部显式指定)
func (b *BaseModel) BeforeCreate(tx *gorm.DB) error {
    if b.ID == uuid.Nil {
        b.ID = uuid.Must(uuid.NewV7())
    }
    return nil
}
```

各 model 内嵌 `BaseModel`(删除各自重复的 `ID/CreateTime/UpdateTime` 三行)。

> **替代方案**(不想引入基类):在每个 model 各加 `BeforeCreate`。侵入更小但代码重复 8 次。如不想改结构,可用全局 callback:
> ```go
> db.Callback().Create().Before("gorm:create").Register("assign_uuid_v7", assignUUIDV7)
> ```
> 其中 `assignUUIDV7` 通过反射定位名为 `id` 且类型为 `uuid.UUID` 的字段。**推荐用 BaseModel,最清晰**。

### 2.3 GORM 零值陷阱(必须理解)

GORM 对 `int` 主键会视 `0` 为「未设置」并省略,让 DB 填默认值;**但对 `uuid.UUID`,零值(nil UUID `00000000-...`)会被当有效值发送,覆盖 DB 的 `default uuidv7()`**。因此:
- **必须**在 Go 端 `BeforeCreate` 预生成(D1)。
- 即使列上写了 `DEFAULT uuidv7()`,也只是兜底(手工 SQL 插入时用)。

## 3. 数据库层改动([docs/db.md](db.md))

由于无历史数据(D4),**直接用新 DDL 建表**,无需迁移脚本。每张表的统一改动:

| 元素 | 旧 | 新 |
|---|---|---|
| 主键 | `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | `id UUID PRIMARY KEY DEFAULT uuidv7()` |
| 普通外键列 | `xxx_id BIGINT NOT NULL` | `xxx_id UUID NOT NULL` |
| **可空外键(哨兵列)** | `root_id BIGINT NOT NULL DEFAULT 0` | `root_id UUID`(允许 NULL,去掉 DEFAULT 0) |
| 批量更新 SQL 的 jsonb 类型 | `AS v(comment_id BIGINT, delta BIGINT)` | `AS v(comment_id uuid, delta BIGINT)` |

### 3.1 各表可空列清单(D2,需改 NULLABLE)

| 表 | 列 | 旧默认值 | 新语义 |
|---|---|---|---|
| `comment` | `root_id` | `DEFAULT 0` | `NULL` = 顶层评论 |
| `comment` | `reply_to_id` | `DEFAULT 0` | `NULL` = 非回复 |
| `comment` | `reply_to_user_id` | `DEFAULT 0` | `NULL` = 非回复 |
| `category` | `parent_id` | `NOT NULL DEFAULT 0` | `NULL` = 顶级分类 |
| `circle` | `category_id` | `NOT NULL DEFAULT 0` | `NULL` = 无分类(或设为 NOT NULL,业务强制选分类) |
| `comment_like` | `post_id` | `DEFAULT 0` | `NULL` = 仅评论点赞时未冗余 |

> 决策点(实施时定):`circle.category_id` 是否允许 NULL。当前 DDL `DEFAULT 0` 允许无分类,建议保持可空。

### 3.2 Category 种子数据(D3)

种子 INSERT 必须固化 UUID(否则每次重建库 ID 变化,导致前端缓存/配置错乱)。示例:
```sql
INSERT INTO domains.category (id, name, slug, parent_id, sort) VALUES
('0190a8b1-0000-7000-8000-000000000001', '科技数码', 'tech', NULL, 100),
('0190a8b1-0000-7000-8000-000000000002', '游戏电竞', 'gaming', NULL, 95),
...
```
> 用一组固定的 UUIDv7(同一毫秒前缀 + 递增尾数),保持字典序与 `sort` 一致无关——排序仍由 `sort` 列控制,UUID 仅作主键。

### 3.3 索引

唯一索引、复合索引语义不变,`uuid` 类型照样支持:
- `idx_member_unique(circle_id, user_id)` ✅
- `idx_comment_post_root_like(post_id, root_id, like_count DESC)` ✅(root_id 为 uuid,可参与索引)
- 部分索引 `WHERE deleted = 0` 等不变

### 3.4 AutoMigrate 现状(顺带修正)

[pkg/server/storage/db/pgsql/connect.go:48-49](../pkg/server/storage/db/pgsql/connect.go) 当前只 `AutoMigrate` 了 `SysUser` 和 `Comment`,遗漏其余 6 个 model。建议二选一:
- **(推荐)以 db.md 的 DDL 为准,用 psql 执行建表**,移除/缩减 AutoMigrate(UUID + 默认值由 DDL 保证,语义最可控)。
- 或把 AutoMigrate 补全为全部 8 个 model,并验证 `AutoMigrate` 对 `type:uuid;default:uuidv7()` 的识别。

### 4.2 受影响的查询模式

| 文件 | 旧 | 新 |
|---|---|---|
| [comment.go:51](../pkg/server/model/comment.go) `if comment.RootID > 0` | 数值比较 | `if comment.RootID != nil` |
| [comment.go:77](../pkg/server/model/comment.go) `root_id = ? AND deleted = ?`, 传 `0` | 顶层评论 | `root_id IS NULL AND deleted = ?` |
| [comment.go:96,268](../pkg/server/model/comment.go) `root_id = ?` | 子回复 | 传 `uuid.UUID` |
| [category.go:38](../pkg/server/model/category.go) `parent_id = ?` 传 `0` | 顶级分类 | `parent_id IS NULL` |

### 4.3 集合/Map 类型

```go
GetUsersByIDs(...)     map[int64]*SysUser      → map[uuid.UUID]*SysUser
GetCirclesByIDs(...)   map[int64]*Circle       → map[uuid.UUID]*Circle
GetJoinedCircleIDsByUserID ... Pluck(..., &circleIDs)  []int64 → []uuid.UUID
GetPostsMediaByIDs(...) map[int64]MediaExtraJSON → map[uuid.UUID]MediaExtraJSON
```

### 4.4 评论游标分页(重点,[comment.go:153-298](../pkg/server/model/comment.go))

- cursor 编码:`"id": float64(comment.ID)` → **`"id": comment.ID.String()`**(UUID 无法转 float)。
- decode:`id := int64(values["id"].(float64))` → `id, _ := uuid.Parse(values["id"].(string))`。
- keyset 条件 `(like_count < ?) OR (like_count = ? AND id < ?)`:**不变**,PG `uuid` 支持 `<` 字典序比较,UUIDv7 下 `id < ?` 等价「更早创建」,与 `ORDER BY id DESC` 配合正确。
- `buildNextCursor` / `applyCursorCondition` / `applyOrderBy` 同步改类型签名。

> ⚠️ cursor 的 base64 内容变更 → 旧客户端持有的 cursor 失效。无历史数据,影响可忽略;若仍担心,加版本前缀。

| **P7** | S3 路径;AutoMigrate 处理(DDL 建表或补全 migrate);全量编译 + 跑通建库 | 端到端通 |
| **P8** | 端到端冒烟(注册→建圈→发帖→评论→点赞→搜索→退出),核对 ES 排序与缓存键 | 验收 |

P1–P6 之间无强编译依赖,可并行;但**整体须同时落地**才能联调(库列已是 UUID,model 不改则跑不通)。建议在一份 PR 内完成 P0–P7。

## 12. 风险与检查清单

1. **[高] GORM 零值覆盖默认值** — 必须 Go 端 `BeforeCreate` 生成,勿依赖 `default:uuidv7()`(D1)。
2. **[高] 哨兵列 IS NULL 改造** — 遗漏任一处 `root_id = 0` / `> 0` 会导致评论层级/分类查询错乱(D2)。全局搜索 `root_id`、`parent_id`、`reply_to`、`= ?` 配合 `0` 逐一核对。
3. **[中] 评论游标 cursor 类型** — float→string,base64 内容变更(无数据可忽略)。
4. **[中] ES mapping 类型** — 必须 `keyword`;若误留 `long`,UUID 字符串无法写入或排序错乱。务必核对 post 索引也建了新 mapping。
5. **[中] MQ jsonb 类型** — `BIGINT`→`uuid` 漏改会导致批量更新 SQL 报类型不匹配。
6. **[低] sa-token 重登** — loginID 格式变更,新服务器无用户,影响可忽略。
7. **[低] Category 种子 UUID 固化** — 必须固定值,不可每次随机。
8. **[低] `int64(userID)` 强转残留** — 编译期可发现,`go build` 即暴露。
9. **[核查] 排序语义** — 抽测「圈子帖子列表/最新」「评论 keyset 翻页」确认仍为时间倒序。
